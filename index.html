真实项目用的是 class-validator：规则写在 DTO 上，校验管道在入口处全局注册一次：

每个字段的条件则贴在 DTO 上，例如岗位管理的 CreatePostDto：

第七阶段：模块化

当项目开始变大：

不推荐

controllers/
services/
repositories/

里面塞几十个甚至上百个文件。

更推荐：按业务领域组织

users/
├── user.controller.ts
├── user.service.ts
├── user.repository.ts
├── user.dto.ts
└── user.entity.ts

auth/
├── auth.controller.ts
├── auth.service.ts
└── auth.dto.ts
这是一种按业务领域组织代码（Feature / Domain-oriented Organization）的方式。

真实项目示例：按业务领域划分模块

真实项目有近 300 个源文件，全部按这个思路组织。顶层只有三块：common/ 横切基础设施、config/ 配置、module/ 业务模块：

真实项目 · 目录结构（节选）

src/
├── common/            # 横切基础设施：守卫、过滤器、装饰器、统一响应
├── config/            # 多环境配置（YAML）
└── module/            # 按业务领域划分

    ├── system/        # 管理后台：auth、user、role、menu、tenant…（15 个子模块）
    │   └── post/      # 拆开一个子模块看内部：
    │       ├── post.controller.ts
    │       ├── post.service.ts
    │       ├── post.module.ts
    │       ├── dto/index.ts
    │       └── entities/post.entity.ts
    ├── monitor/       # 监控：登录日志 / 操作日志 / 在线用户 / 定时任务
    ├── upload/        # 文件上传

模块与耦合

高内聚，低耦合的场景与判断

这个问题其实比“什么是高内聚、低耦合”更重要。你真正需要掌握的不是“要不要使用高内聚低耦合”，而是：

“什么时候代码的变化开始互相影响，我需要开始拆分？”

Core Mindset

高内聚、低耦合不是一种架构，
而是一种判断标准。

一句话判断法

以后写 TS 后端时，可以先问自己两个问题：

问题 1

这些代码是不是因为同一个原因而变化？

是放在一起 → 高内聚

否考虑拆开

问题 2

A 修改的时候，是否经常必须修改 B？

是耦合过高 → 考虑降低耦合

否没必要为了“低耦合”强行抽象

所以：

高内聚

解决“东西应该放在哪里”。

低耦合

解决“东西之间应该怎么依赖”。

这个区别非常重要。

真正的判断标准：变化概率 × 影响范围

推荐用这个思维：

支付服务高大✅
邮件服务高中✅
第三方 AI API高大✅
核心业务规则高大✅

这比“架构书说 Repository 很重要，所以我要 Repository”靠谱得多。

比如把一个简单的邮箱校验拆成四个文件：

非常实用的经验法则：5 个信号

信号 1

一个文件越来越大

100 行 → 200 行 → 500 行 → 1000 行。开始检查职责。

信号 2

一个类经常因为不同的事情修改

支付改一次、订单改一次、库存改一次、邮件改一次，结果 OrderService 一直在改。这是内聚性下降的信号。

信号 3

一个模块修改，经常导致其他模块一起修改

修改 User → Auth 要改 → Order 要改 → Payment 又要改。这是耦合过高的信号。

信号 4

你无法单独测试某个业务

测试 CreateOrder 却必须启动 PostgreSQL、Redis、第三方支付、消息队列。说明业务逻辑和基础设施耦合严重，可以考虑抽象。

信号 5

你开始出现大量 if provider === xxx

OpenAI、DeepSeek、Gemini、Claude、Ollama…… 越来越多。这是非常典型的变化点没有被隔离，此时接口 + 策略 / Provider 抽象就很有价值。

最终决策树

以后写代码的时候，脑子里可以过一遍：

最重要的一句话

记住这句话

高内聚不是“拆得越细越好”，低耦合也不是“抽象越多越好”。
真正的架构能力，是识别代码的变化边界，
把经常一起变化的东西放在一起，把容易独立变化的东西隔离开。

所以以后看到一个新需求，不要第一反应“我要不要上 Clean Architecture？”，而是先问：

Q1 谁负责这个业务？
Q2 哪些代码会因为这个需求一起变化？
Q3 哪些代码未来可能独立变化？
Q4 这次变化会影响多少地方？
Q5 如果现在不抽象，未来修改成本有多大？
这 5 个问题，比背 DDD、SOLID、Clean Architecture 有用得多。

第十阶段：架构演进

成熟项目可以进一步组织成：

每一部分各司其职：

modules/

业务模块 · 按业务域切分

  • 每个模块对应一个业务能力（users、auth），内部自成一体，互不 import 对方内部细节。

modules/users/domain/

领域层 · 业务核心

  • entities/ 实体：核心业务对象，承载业务规则（如 User）。
  • value-objects/ 值对象：不可变的小型业务概念（如 Email）。
  • repositories/ 仓储接口：只声明“需要什么数据”，不关心怎么存。

modules/users/application/

应用层 · 用例编排

  • use-cases/ 用例：一个完整业务动作的流程（如 RegisterUserUseCase）。
  • dto/ 入参 / 出落数据结构，把外部数据和领域对象隔开。

modules/users/infrastructure/

基础设施层 · 技术实现

  • repositories/ 仓储实现：用 Prisma / SQL 真正读写数据库。
  • 其它技术细节也放这里：外部 API、缓存、消息队列……

modules/users/presentation/

表现层 · 对外接口

  • controllers/ 控制器：解析 HTTP 请求、调用用例、返回响应，不写业务逻辑。

shared/

跨模块共享

  • errors/ 统一错误类型；utils/ 通用工具；types/ 公共类型。只放真正通用的东西。

config/

配置

  • 读取并校验环境变量：数据库连接、密钥、端口……只在这里出现一次。

main.ts

组合根 · 启动入口

  • 把实现注入接口、注册路由、启动服务——整个应用在这里被“组装”起来。
依赖只指向内层：presentation → application → domain；infrastructure 实现 domain 定义的接口。

Redis 缓存与多库组合

接口变慢，多数时候不是代码写得差，而是每次请求都在重复做昂贵的事：查数据库、算数据、调外部服务。

两条最常用的提效路线：

① 加缓存：同样的查询，别每次都打到数据库 ② 多库组合：让合适的数据库干合适的活

真实项目示例：方法级缓存装饰器

「读多写少」的数据（配置、字典、权限），每次请求都查 MySQL 太浪费。真实项目把缓存做成了方法级装饰器，业务方法体里一行缓存代码都没有：

  • 业务代码与缓存逻辑彻底解耦——这是 AOP（面向切面）思想：横切关注点抽到装饰器里
  • 只缓存「读多写少、能容忍短暂旧值」的数据
  • 每个写操作都配套一个 @CacheEvict，否则用户会读到旧数据

一次带缓存的请求流程：

请求进来
先查 Redis 缓存
命中 → 直接返回（微秒级）
未命中 → 查 MySQL，结果写回 Redis

真实项目里 Redis 不只做缓存，它承担的是所有「快、可丢、会过期」的数据：

登录会话

JWT 里只放 uuid，真正的会话在 Redis——删掉 key 即强制登出，Token 无需等它过期

配置 / 字典缓存

@Cacheable 读多写少的数据，命中率极高

验证码

写入后设 5 分钟过期，到期自动消失，无需清理任务

在线用户

扫描登录 Token 的 key 就能列出在线用户、踢人下线

缓存不是免费的：引入它就引入了数据不一致的可能。「更新数据库 + 同步失效缓存」必须成对出现，这正是 @CacheEvict 存在的意义。

多数据库组合：按数据特点分类

没有一种数据库什么都能干好。真实项目按「数据的读写模式」给数据分类，再各自选存储：

MySQL

关系型

用户、角色、菜单、课程、订单——要事务、要关联查询的结构化数据

Redis

内存 KV

会话、缓存、验证码——读写极快、可过期、丢了能重建

ChromaDB

向量库

文档切片的 Embedding——按语义找「相似」，而不是「相等」

一个接口同时用到三种库的真实例子——AI 知识库的文档入库：

元数据进关系型库（要查询、要展示列表），向量进向量库（要语义检索）——各存各的长处，接口负责编排。

市面上的企业级数据库：利与弊

组合之前，先把市面上的主流选手认清。同样是「存数据」，不同库的设计取舍完全不同，利与弊是一体两面——它擅长的事，就是它不擅长的另一面：

API 版本化：什么时候要 /v1？

/v1 的意义不在于"标记第一个版本"，而在于：你能不能同时养活两个契约版本。

接口第一次上线时，没有人会想版本号。这个问题真正出现，是在第一次"不得不破坏契约"的时刻：字段要改名、响应结构要调整，而调用方已经在用了。这时 URL 里有没有 /v1，决定了你有没有退路。

判断标准：有没有"升不动"的调用方

URL 版本号解决的问题只有一个——旧客户端还活着，接口契约却变了。所以先盘点你的调用方：

  • 对外开放 API（第三方、合作伙伴）：微信支付、飞书开放平台的接口都带版本。调用方按自己的节奏升级，你无法协调发版，破坏性变更只能开 /v2。
  • 移动端 App 的后端：应用商店审核要几天，用户不点更新，旧客户端会存活几个月甚至几年，契约必须能并行存在多份。很多团队第一天就加 /v1，就是给将来留这条退路。
  • B2B 集成、Webhook 回调地址：对方系统里写死了 URL，事后改契约的成本极高。

什么情况下不需要 /v1

反过来，如果所有调用方都和你一起发版，URL 上的 /v1 就只是仪式：

  • 自家 Web 前端：前后端同仓库、同一条发布流水线，浏览器永远加载最新前端，不存在"旧客户端"。
  • 内部微服务之间：版本用包版本号、契约测试来表达。URL 上写 /v1 反而让人产生"v1 里可以随便改"的错觉。
  • GraphQL：不用 URL 版本，用 @deprecated 标记字段、渐进下线。
  • BFF 层：BFF 的版本就是前端发版版本，隐式绑定。

真正的成本：不是三个字符，是 N 套契约

版本化的开销不是 URL 里多三个字符，而是同时维护多套契约：双份路由、双份文档、双份测试、双份客户端 SDK，并且要一直养到最后一方迁走为止：

所以两条推论：

  • 不要预防性版本化：还没有第二类调用方之前，别急着上 /v2。
  • 版本号是承诺：/v1 存在的每一天，你都要养着它。

大厂怎么做：企业级案例

把上面的判断放进真实世界，国内开放平台同样分两派——大版本进 URL，还是把版本藏进请求参数：

大版本进 URL · 微信支付 / 钉钉 / 飞书 / 高德 / 大模型 API vs 版本藏进参数 · 支付宝 / 淘宝开放平台

微信支付

URL 大版本 · 新旧长期并行

V2 时代 URL 里没有版本（pay/unifiedorder）；V3 重设计把 /v3 写进 URL（api.mch.weixin.qq.com/v3/pay/...），签名、证书、加密整套换掉。V2/V3 并行至今，V2 只维护不加功能——破坏性变更开新版本，绝不悄悄改旧的。

钉钉

新旧域名并存

旧服务端接口在 oapi.dingtalk.com（URL 无版本）；新版统一为 api.dingtalk.com/v1.0/...，主版本直接进 URL。大厂自己"补票"的方式：契约无法平滑兼容时，新域名 + 新版本一起翻篇，旧接口只维护。

飞书

资源级版本（粒度最细）

open.feishu.cn/open-apis/im/v1/messages、/contact/v3/users：版本号跟到每个资源对象——消息接口还在 v1，通讯录已经到 v3，谁破坏兼容谁单独升版本，互不拖累。

支付宝 / 淘宝开放平台

网关固定 · 版本进参数

网关地址永远是 openapi.alipay.com/gateway.do，接口靠 method + version 参数区分（淘宝 TOP 同理，公共参数 v=2.0）——版本号的另一种藏法：不在 URL，在请求参数里，网关按参数路由到对应实现。

高德地图

v3 / v5 并行

restapi.amap.com/v3/geocode/geo 仍在服务，搜索、路径规划已升级到 /v5/...，官方提供逐接口的迁移对照表。响应结构频繁增强的 API，靠大版本 URL 把承诺划清楚。

国产大模型 API

兼容性 /v1

智谱 open.bigmodel.cn/api/paas/v4/chat/completions、Moonshot api.moonshot.cn/v1/...；DeepSeek 文档写得更直白：/v1 与模型版本无关，纯粹为了兼容 OpenAI SDK——为了接入生态，/v1 也可以只是仪式。

国内开放平台的共同点：版本绑定的是契约而不是代码；弃用与迁移窗口白纸黑字（微信支付 V2 长期只维护、高德给逐接口迁移指南）；升级永远由调用方发起。选哪一派，只取决于一件事——调用方能不能跟你同步发版。

什么才算"破坏性变更"

内部接口想做到"永远不需要版本号"，靠的是只做非破坏变更。判断标准：

只要坚持"只做非破坏变更"，内部接口就永远不需要版本号——而这件事靠 TypeScript 类型、OpenAPI codegen、tRPC 这类类型契约兜底，不靠 URL。

反过来讲，内部接口不加 /v1，反而是给自己留了"用完即改"的灵活性——这正是提效的来源。版本号不是规范加分项，是用灵活性换兼容性的交易，只在有调用方接不住时才做。

Rule of Thumb

有升不动的外部调用方，就加 /v1；
调用方都跟你一起发版，就不加——靠兼容式演进和类型契约兜底。

后端框架对比

学完分层之后，再单独横向看一遍框架：所有框架解决的都是同一件事——「HTTP 请求进来，怎么路由到处理函数、怎么取参数、怎么校验、怎么返回响应」。区别只在「框架替你做多少」。

把常见后端框架分成三类来对比，一一覆盖：

① TS/Node 后端框架 ② 全栈框架（前后端一体） ③ 跨语言对照：FastAPI / Gin

TS/Node 后端框架：两大家族

按「框架替你做多少」，TS/Node 后端框架可以分成两大家族：

微内核：路由 + 中间件

框架只管把请求接到处理函数，分层、校验、DI 都要自己搭。灵活，但架构靠自觉。

请求拦截器与响应拦截器

拦截器回答的问题是：所有接口都要走的那段公共逻辑，放在哪？答案是在管道上——请求进来、响应出去的必经之路，统一拦截一次。

一个请求从进来到响应出去，中间是一条完整的管道。除了 Controller 里的业务逻辑，还有一类"每个接口都需要"的公共逻辑：校验 Token、记日志、限流、把返回值包成统一响应格式……这些逻辑写进每个接口就是灾难。拦截器（Interceptor）就是在管道上统一拦一次的机制：请求侧拦一次，响应侧拦一次。

请求拦截器：进门检查

在请求到达 Controller 之前执行，干的是"进门检查"的活——所有请求都要做、但跟具体业务无关的事：

  • 身份认证：校验 Token，解析出 userId、tenantId 挂到 request 上，后面的代码直接取用。
  • 日志与链路追踪：生成 requestId、记录请求入参，一次请求从头到尾可追踪。
  • 限流与防刷：同一 IP / 用户短时间内请求过多，直接拒绝。
  • 数据预处理：请求体解密、Header 规范化、白名单路由放行。

关键行为是短路：检查不通过就直接返回错误响应，Controller 根本不会执行——这就是"拦截"两个字的本意。

响应拦截器：出门包装

在响应离开 Controller 之后执行，干的是"出门统一包装"的活：

  • 统一响应格式：把 Controller 返回的裸数据包成 { code, msg, data }（第 14 节的 ResultData，下一节代码见）。
  • 响应日志：记录路径、状态码、耗时，接口慢了一目了然。
  • 缓存处理：命中缓存直接返回，或给响应加上缓存标记。
  • 敏感信息过滤：统一剔除或脱敏不该出现在响应里的字段。

五种机制怎么分工？

NestJS 把管道拆成了几种角色，初学最容易混。按"管什么"来记：

机制 管什么 典型例子
中间件 Middleware请求的进出，框架级，不知道有 ControllerCORS、body 解析、请求日志
守卫 Guard能不能进（认证与授权）JWT 校验、角色权限
拦截器 Interceptor进出各加一层，能改请求也能改响应统一响应包装、耗时日志、缓存
管道 Pipe参数对不对校验 DTO、类型转换（第 12 节）
过滤器 Filter出错了怎么办全局异常 → 统一失败响应（第 13 节）

Express / Koa 没有这些细分角色，全部用中间件表达：一个中间件里 next() 之前是请求侧，之后是响应侧——本质相同：

写过前端的话，这个词你大概率在 axios 里见过：interceptors.request.use 给每个请求统一带上 Token，interceptors.response.use 把统一响应"拆"开、401 自动跳登录。后端的拦截器是同一件事换了一边：前端在浏览器里"加 Token、拆响应"，后端在服务器里"验 Token、装响应"——同一个统一响应契约，两端各有一个拦截器在维护。

什么该放进拦截器

  • 该放：所有请求都要走一遍、且与具体业务无关的逻辑——认证、日志、追踪、限流、统一包装。
  • 该放：希望将来能全局统一调整的策略——日志格式升级、响应加追踪头，改一处即可。
  • 不该放：只跟某个业务有关的判断。"VIP 用户列表多返回一个字段"是 Service 的事，塞进拦截器就是污染。
  • 不该放：需要被大量接口单独绕过的逻辑。真有例外，用装饰器做开关（如 @SkipTransform()），别在拦截器里堆 if-else。
拦截器是全局魔法：看不见，但处处生效。往里放的每一条逻辑，所有接口都要一起承担——放得越少、越通用越好；一旦开始写业务 if-else，就该搬回 Service 了。

Rule of Thumb

每个接口都要做的事，不在接口里写——
放进拦截器，管道上写一次。
