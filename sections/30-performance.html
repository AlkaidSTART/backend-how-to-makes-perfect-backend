接口提效

Redis 缓存与多库组合

接口变慢，多数时候不是代码写得差，而是每次请求都在重复做昂贵的事：查数据库、算数据、调外部服务。

两条最常用的提效路线：

① 加缓存：同样的查询，别每次都打到数据库 ② 多库组合：让合适的数据库干合适的活

真实项目示例：方法级缓存装饰器

「读多写少」的数据（配置、字典、权限），每次请求都查 MySQL 太浪费。真实项目把缓存做成了方法级装饰器，业务方法体里一行缓存代码都没有：

  • 业务代码与缓存逻辑彻底解耦——这是 AOP（面向切面）思想：横切关注点抽到装饰器里
  • 只缓存「读多写少、能容忍短暂旧值」的数据
  • 每个写操作都配套一个 @CacheEvict，否则用户会读到旧数据

一次带缓存的请求流程：

请求进来
先查 Redis 缓存
命中 → 直接返回（微秒级）
未命中 → 查 MySQL，结果写回 Redis

真实项目里 Redis 不只做缓存，它承担的是所有「快、可丢、会过期」的数据：

登录会话

JWT 里只放 uuid，真正的会话在 Redis——删掉 key 即强制登出，Token 无需等它过期

配置 / 字典缓存

@Cacheable 读多写少的数据，命中率极高

验证码

写入后设 5 分钟过期，到期自动消失，无需清理任务

在线用户

扫描登录 Token 的 key 就能列出在线用户、踢人下线

缓存不是免费的：引入它就引入了数据不一致的可能。「更新数据库 + 同步失效缓存」必须成对出现，这正是 @CacheEvict 存在的意义。

多数据库组合：按数据特点分类

没有一种数据库什么都能干好。真实项目按「数据的读写模式」给数据分类，再各自选存储：

MySQL

关系型

用户、角色、菜单、课程、订单——要事务、要关联查询的结构化数据

Redis

内存 KV

会话、缓存、验证码——读写极快、可过期、丢了能重建

ChromaDB

向量库

文档切片的 Embedding——按语义找「相似」，而不是「相等」

一个接口同时用到三种库的真实例子——AI 知识库的文档入库：

元数据进关系型库（要查询、要展示列表），向量进向量库（要语义检索）——各存各的长处，接口负责编排。

市面上的企业级数据库：利与弊

组合之前，先把市面上的主流选手认清。同样是「存数据」，不同库的设计取舍完全不同，利与弊是一体两面——它擅长的事，就是它不擅长的另一面：

数据库 利（擅长） 弊（短板） 典型场景
MySQL关系型 生态最大、资料最多：主从复制、分库分表、云托管方案一应俱全，招人最容易 复杂查询和高级类型偏弱：JSON / 数组 / GIS 不如 PostgreSQL，复杂 SQL 的优化器偏保守 电商、SaaS 等核心业务库；本教程示例的默认选择
PostgreSQL关系型 功能天花板：JSONB、数组、窗口函数、递归 CTE、内置全文检索；扩展生态强——PostGIS 管地理、pgvector 管向量，一个库顶三个 每个连接占一个进程，高并发必须配连接池（PgBouncer）；国内传统运维积累比 MySQL 少 复杂报表、GIS、AI 应用；新项目越来越首选它
SQLite嵌入式关系型 零部署零运维，单文件就是整个库；进程内访问没有网络开销，读性能极高；全球装机量第一——每台手机里都有 没有服务端进程，多台机器共享数据要自己想办法；写入是单写者串行，扛不住服务端高并发写 移动 / 桌面应用本地存储；小工具、原型、自动化测试
MongoDB文档型 Schema 灵活免迁移，嵌套文档一次读全；副本集 + 分片内建，水平扩展省心 跨文档关联弱（$lookup 慢且难维护）；多文档事务 4.0+ 才有且代价高；没有约束的 Schema 全靠应用层纪律 内容管理、商品详情、埋点日志；需求快变的原型
Redis内存 KV 微秒级读写；String / Hash / ZSet 等结构丰富；TTL 自动过期内建 内存贵，放不下全量数据；持久化只是兜底，不能当主存；没有查询语言 缓存、会话、验证码、排行榜（上一节刚讲）
Elasticsearch搜索引擎 倒排索引支撑全文检索与相关性排序，聚合分析能力强 吃内存吃 CPU；近实时、非强一致；六个里运维复杂度最高的一个 商品搜索、站内搜索、日志分析（ELK）
同类型二选一时（最典型是 MySQL vs PostgreSQL），团队熟不熟、云厂商托管支不支持、招人好不好招，往往比功能清单更有决定权——功能差距再大，也大不过「出了事没人会修」。

拿不准时，按数据的形状对号入座：

你的数据长这样 就选
要事务、多表关联、强一致MySQL / PostgreSQL
字段多变、嵌套深、按整篇文档读写MongoDB（或 PostgreSQL 的 JSONB）
跑在用户设备里、单机、不想装服务SQLite
读要极快、可丢、会过期Redis
关键词搜索、日志、按相关性排序Elasticsearch
按语义找「相似」而不是「相等」向量库：ChromaDB / pgvector / Milvus

再往后还有一批更专业的品类，认识名字即可，真遇到对应需求再学：

ClickHouse：列存分析 DuckDB：嵌入式分析 TiDB：分布式 NewSQL InfluxDB：时序 Neo4j：图
组合的原则：按数据特点选存储，而不是按技术热度。绝大多数项目 MySQL + Redis 已经够用；等真的出现全文检索、向量检索的需求，再引入对应组件。

再往后，规模逼出来还有这些手段，知道即可、不要提前上：
