模块与耦合

高内聚，低耦合的场景与判断

这个问题其实比“什么是高内聚、低耦合”更重要。你真正需要掌握的不是“要不要使用高内聚低耦合”，而是：

“什么时候代码的变化开始互相影响，我需要开始拆分？”

Core Mindset

高内聚、低耦合不是一种架构，
而是一种判断标准。

一句话判断法

以后写 TS 后端时，可以先问自己两个问题：

问题 1

这些代码是不是因为同一个原因而变化？

是放在一起 → 高内聚

否考虑拆开

问题 2

A 修改的时候，是否经常必须修改 B？

是耦合过高 → 考虑降低耦合

否没必要为了“低耦合”强行抽象

所以：

高内聚

解决“东西应该放在哪里”。

低耦合

解决“东西之间应该怎么依赖”。

这个区别非常重要。

真正的判断标准：变化概率 × 影响范围

推荐用这个思维：

是否需要抽象 = 变化概率 × 影响范围
东西 变化概率 影响范围 是否值得抽象
User Service低小❌
Prisma 查询中中⚠️
支付服务高大✅
邮件服务高中✅
第三方 AI API高大✅
核心业务规则高大✅

这比“架构书说 Repository 很重要，所以我要 Repository”靠谱得多。

非常实用的经验法则：5 个信号

信号 1

一个文件越来越大

100 行 → 200 行 → 500 行 → 1000 行。开始检查职责。

信号 2

一个类经常因为不同的事情修改

支付改一次、订单改一次、库存改一次、邮件改一次，结果 OrderService 一直在改。这是内聚性下降的信号。

信号 3

一个模块修改，经常导致其他模块一起修改

修改 User → Auth 要改 → Order 要改 → Payment 又要改。这是耦合过高的信号。

信号 4

你无法单独测试某个业务

测试 CreateOrder 却必须启动 PostgreSQL、Redis、第三方支付、消息队列。说明业务逻辑和基础设施耦合严重，可以考虑抽象。

信号 5

你开始出现大量 if provider === xxx

OpenAI、DeepSeek、Gemini、Claude、Ollama…… 越来越多。这是非常典型的变化点没有被隔离，此时接口 + 策略 / Provider 抽象就很有价值。

最终决策树

以后写代码的时候，脑子里可以过一遍：

最重要的一句话

记住这句话

高内聚不是“拆得越细越好”，低耦合也不是“抽象越多越好”。
真正的架构能力，是识别代码的变化边界，
把经常一起变化的东西放在一起，把容易独立变化的东西隔离开。

所以以后看到一个新需求，不要第一反应“我要不要上 Clean Architecture？”，而是先问：

Q1 谁负责这个业务？
Q2 哪些代码会因为这个需求一起变化？
Q3 哪些代码未来可能独立变化？
Q4 这次变化会影响多少地方？
Q5 如果现在不抽象，未来修改成本有多大？
这 5 个问题，比背 DDD、SOLID、Clean Architecture 有用得多。
