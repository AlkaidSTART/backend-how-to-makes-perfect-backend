模块与耦合

第七阶段：模块化

当项目开始变大：

不推荐

controllers/
services/
repositories/

里面塞几十个甚至上百个文件。

更推荐：按业务领域组织

users/
├── user.controller.ts
├── user.service.ts
├── user.repository.ts
├── user.dto.ts
└── user.entity.ts

auth/
├── auth.controller.ts
├── auth.service.ts
└── auth.dto.ts
这是一种按业务领域组织代码（Feature / Domain-oriented Organization）的方式。

真实项目示例：按业务领域划分模块

真实项目有近 300 个源文件，全部按这个思路组织。顶层只有三块：common/ 横切基础设施、config/ 配置、module/ 业务模块：

真实项目 · 目录结构（节选）

src/
├── common/            # 横切基础设施：守卫、过滤器、装饰器、统一响应
├── config/            # 多环境配置（YAML）
└── module/            # 按业务领域划分
    ├── main/          # C 端业务：课程 / 训练营 / 考试
    ├── system/        # 管理后台：auth、user、role、menu、tenant…（15 个子模块）
    │   └── post/      # 拆开一个子模块看内部：
    │       ├── post.controller.ts
    │       ├── post.service.ts
    │       ├── post.module.ts
    │       ├── dto/index.ts
    │       └── entities/post.entity.ts
    ├── monitor/       # 监控：登录日志 / 操作日志 / 在线用户 / 定时任务
    ├── upload/        # 文件上传
    ├── rag/           # AI 知识库（RAG：文档入库 / 向量检索）
    ├── ai-config/     # AI 供应商与提示词配置
    └── health/        # 健康检查
「岗位」的路由、业务、表结构、DTO 全部收在 system/post/ 一个目录里。改岗位功能只需打开一个目录，不需要在全局的 controllers/、services/ 之间来回跳——这就是模块化在真实项目里的收益。
