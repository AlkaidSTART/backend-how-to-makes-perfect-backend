进阶架构

第十阶段：架构演进

成熟项目可以进一步组织成：

每一部分各司其职：

modules/

业务模块 · 按业务域切分

  • 每个模块对应一个业务能力（users、auth），内部自成一体，互不 import 对方内部细节。

modules/users/domain/

领域层 · 业务核心

  • entities/ 实体：核心业务对象，承载业务规则（如 User）。
  • value-objects/ 值对象：不可变的小型业务概念（如 Email）。
  • repositories/ 仓储接口：只声明“需要什么数据”，不关心怎么存。

modules/users/application/

应用层 · 用例编排

  • use-cases/ 用例：一个完整业务动作的流程（如 RegisterUserUseCase）。
  • dto/ 入参 / 出落数据结构，把外部数据和领域对象隔开。

modules/users/infrastructure/

基础设施层 · 技术实现

  • repositories/ 仓储实现：用 Prisma / SQL 真正读写数据库。
  • 其它技术细节也放这里：外部 API、缓存、消息队列……

modules/users/presentation/

表现层 · 对外接口

  • controllers/ 控制器：解析 HTTP 请求、调用用例、返回响应，不写业务逻辑。

shared/

跨模块共享

  • errors/ 统一错误类型；utils/ 通用工具；types/ 公共类型。只放真正通用的东西。

config/

配置

  • 读取并校验环境变量：数据库连接、密钥、端口……只在这里出现一次。

main.ts

组合根 · 启动入口

  • 把实现注入接口、注册路由、启动服务——整个应用在这里被“组装”起来。
依赖只指向内层：presentation → application → domain；infrastructure 实现 domain 定义的接口。

这是 Clean Architecture / DDD 等思想可以演进到的方向之一。但是：

!
不要在刚学后端时直接套这个目录结构。

架构应该根据复杂度演进。
